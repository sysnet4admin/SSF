# 6회차: CI

## 이번 시간의 목표

지금까지 강사가 만든 이미지를 썼다. 이제 내 코드를 push하면 GitHub Actions가 자동으로 내 이미지를 빌드하게 만든다. 그리고 `k8s/`가 내 이미지를 가리키게 바꾼다.

## 지금 단계

앱과 매니페스트는 그대로다. 이미지를 "강사 것"에서 "내 것"으로 바꾼다.

## 핵심 개념

- CI(지속적 통합): 코드를 push하면 자동으로 빌드한다.
- GHCR: GitHub 컨테이너 레지스트리. public으로 두면 인증 없이 pull 된다.
- 자세한 배경은 `decision-guides/ci-cd-tool.md`를 참조한다.

## 진행

### 1. fork

1회차 준비에서 이미 fork 하고 clone 해 두었다면 그대로 사용한다. 아직이라면 저장소(`sysnet4admin/SSF`) 화면 우측 상단의 Fork 버튼을 눌러 본인 저장소(`github.com/본인계정/SSF`)를 만든다.

### 2. fork의 Actions 활성화 (한 번만)

fork한 저장소는 보안상 Actions가 기본으로 꺼져 있다. 본인 저장소의 Actions 탭에 들어가서 "I understand my workflows, go ahead and enable them" 버튼을 한 번 눌러 활성화한다. 이 단계를 건너뛰면 push해도 빌드가 시작되지 않는다.

### 3. push로 빌드 트리거

1회차에 clone 해 둔 `SSF` 폴더에서 작업한다. `app/frontend/src/App.jsx`의 제목 "SSF 15기"를
본인 이름으로 바꾼 뒤 push 한다.

```bash
git add .
git commit -m "My first image"
git push
```

push 하면 `.github/workflows/build.yml`이 동작한다. 빌드는 `app/` 변경에만 반응하므로
`k8s/`만 바꾼 push에는 돌지 않는다.

**빌드 성공을 확인한다.** 본인 저장소의 Actions 탭에 방금 push의 실행이 뜬다. `build (frontend)`와
`build (backend)` 두 job이 모두 초록 체크가 되면 성공이다. 30초 안팎 걸린다. 빨간 X가 뜨면
해당 job을 눌러 로그를 열고 AI에게 그 내용을 물어본다.

제목을 바꾼 결과는 5번에서 내 이미지로 전환한 뒤 화면에 보인다.

### 4. 패키지 public 확인 (필요시 전환)

빌드가 끝나면 GHCR 패키지 두 개(`ssf15-frontend`, `ssf15-backend`)가 생긴다. 본인 GitHub
프로필의 Packages에서 각 패키지를 열어 visibility를 확인한다. private이면 Package settings의
Change visibility에서 Public으로 바꾼다.

public이어야 클러스터가 인증 없이 이미지를 가져온다. Actions가 처음 만든 패키지는 private인
경우가 많으므로 두 개 모두 확인한다.

### 5. 내 이미지로 전환

`prompt-guardrails/switch-image.md`를 따라 `k8s/`의 이미지 주소를 본인 계정으로 바꾼다.

## 확인

```bash
kubectl get deploy backend -o jsonpath='{.spec.template.spec.containers[0].image}'
```

이미지 주소가 본인 계정(`ghcr.io/본인아이디/ssf15-backend:v1`)으로 바뀌면 성공이다. 브라우저를 새로고침하면 본인이 바꾼 화면 제목이 보인다.

> 제목을 다시 고쳐 push 하는 경우, 태그는 그대로 `:v1`이라 노드에 받아 둔 옛 이미지를 쓸 수 있다.
> `k8s/`의 Deployment에 `imagePullPolicy: Always`를 넣어 두었으므로 `kubectl rollout restart`로
> 새 이미지를 다시 받아온다.
